## U-F0 — Integration with the real contract (critical path)
**U-F0.1 Adopt & reconcile** (after getpack-api has tagged a release, U-B0 step 1):
1. `pnpm gen:api --adopt` against the **tagged** release; point `contract.lock.json`'s `source` at the release asset (no more sha256-only pin).
2. Read getpack-api's `docs/contract-requests-triage.md`. Update every row of `docs/contract-requests.md` to `published as <operationId>` / `published differently (see mapping)` / `open — getpack-api U-B0.N` / `rejected (reason)`; regenerate `contract-requests.openapi.json` with only the still-open ones.
3. From getpack-api B6.3: the BFF forwards the client IP (`X-Forwarded-For`, matching the API's `TRUST_PROXY` hop count) so per-IP throttles see the customer, not the BFF; add the admin menu entry `ops` the API now returns.
4. Mocks: regenerate base handlers from contract examples; add error-path handlers from each operation's documented problem codes and a scenario switcher (`?mock=<operationId>:<code>`) for dev and Storybook; map every problem `code` the UI can receive to th/en copy (lint: no unmapped codes for operations the UI calls).

**U-F0.2 / 0.3 / 0.4 Migrate by zone** — customer (`store.*`), admin (`admin.*`), partner (`partner.*`), one session each:
- Move each call site on `awaiting-migration.ts` (and each newly published request) to the published operation; apply the triage mapping where the shape differs; delete the zod request type and the mock override; the generated mock takes over.
- The list may only shrink (existing registry test); the zone is done when none of its entries remain.
- Keep behaviour and copy; where the published shape carries less or more than the screen assumed, follow the contract and record the change in PROGRESS.
- CS calculators must show the API's real results; remove illustrative figures. Only **folding** exists in the backend today; the other six arrive one by one from getpack-api U-B6 — until then their screens show the type as RFQ-only (the API says so), never mocked prices.

**U-F0.5 Real-backend end to end**:
- An `e2e:integration` project that runs the Playwright suite against getpack-api (`API_INTERNAL_URL` → the integration environment or a local `docker compose` + `pnpm db:seed:dev` + worker), with sandbox payment/slip/carrier fakes enabled in the backend.
- Tag tests that can only run on mocks (e.g. time travel) and keep them in the mock project; everything else must pass on the real backend.
- Fix mismatches on this side, or raise a contract request with the failing response attached.
- Acceptance: no `CONTRACT-REQUEST` mock left for any flow in the R1 launch path (D-110); `e2e:integration` green; PROGRESS lists what still waits on the backend, if anything.

## U-F2 — Art direction tokens (D-180)

Replace token **values** only (primitive → semantic mapping stays) with the palette in `design-system.md` §Art direction for light, dark and high-contrast; re-run the contrast gate — every semantic text/UI pair must pass WCAG 2.2 AA; adjust proposed values minimally if a pair fails and record it in PROGRESS.

## U-F3 — Storefront page patterns (D-180, D-181)
Implement `F3-storefront.md` §Page patterns on the existing customer zone:
1. **Header**: sticky, condensing; centred nav; **mega menu** of packaging categories with a chip per item **"ราคาทันที" / "ขอใบเสนอราคา" / "บางสเปก"** from the quote-path / availability data the API provides; mobile full-screen menu with the same chips; announcement bar only when a real campaign is live.
2. **Home — exactly 8 sections** in the specified order (hero with a quick-start strip that deep-links into the configurator with values pre-filled; product-type cards; 4-step process; ready-to-ship stock products; 6 benefits; work & testimonials with the **empty-state variant** when no permitted customer content exists — never invented quotes; articles; newsletter + contact strip + dark footer with Collective Group (Thailand) and tax id). Remove or merge existing sections that do not fit. Below-fold sections lazy-load; the static hero image is the LCP element.
3. **Catalogue**: filter sidebar / mobile sheet (type, material & thickness, printing, size range, MOQ, lead time, availability instant/RFQ, starting price range), applied-filter chips, "ล้างทั้งหมด", toolbar (count, grid/list/compact, sort), URL-synced, server pagination, skeletons, one sidebar campaign card only when a campaign is live.
4. **Product/type page**: gallery switching imagesets, specs, starting price with the quantity it assumes, MOQ, lead-time range, tolerance note, CTA **คำนวณราคาจริง** (carries values into the configurator) + **ออกแบบออนไลน์**; for RFQ-only types CTA **ขอใบเสนอราคา** with the SLA; standard sizes, materials explainer, FAQs, dieline template download.
5. **Card rule (D-181)**: remove any countdown, "only N left" or struck-through price not backed by the API's campaign badge / reference price (getpack-api U-B4); made-to-order cards show starting price per piece, assumed quantity, MOQ and lead time.
6. Acceptance: Lighthouse marketing budget, axe, visual snapshots, e2e (mega menu → type page → configurator with pre-filled values; RFQ-only type → RFQ form), SEO checks unchanged.
